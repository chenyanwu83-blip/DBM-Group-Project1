\subsection{Official Five-Entity Base}
\texttt{Passenger} and \texttt{Driver} each link to many \texttt{Trip} rows through the required \texttt{psg\_id} and \texttt{driver\_id} foreign keys. Under D-05, a Trip row starts when a driver accepts the request; \texttt{start\_time} therefore represents acceptance, not passenger boarding. Each \texttt{Driver} references one \texttt{Vehicle}. The official \texttt{Driver.vehicle\_id UNIQUE} constraint also limits a vehicle to at most one recorded driver, despite the broader $N{:}1$ label in the teacher's sample figure. Each \texttt{Payment} references one Trip, while \texttt{Payment.trip\_id UNIQUE} permits zero or one payment per Trip. The zero case supports the official query for completed but unpaid trips. These are the actual cardinalities enforced by Listing~17, not additional assumptions.

\subsection{Approved Extensions}
The \texttt{pickup\_zone} table gives each accepted trip one named pickup zone through \texttt{trip\_detail.zone\_id}. It supports q09, which counts all accepted Trip rows, including later cancellations; it cannot measure unmatched requests or unmet demand. The \texttt{service\_tier} table stores the four original RideAustin tier names and a descriptive fare multiplier. Its link through \texttt{trip\_detail.service\_tier\_id} supports q10: completed-trip count, average fare, valid per-trip rating count and average rating by tier. The rating is the passenger's rating of this trip, not a driver's historical average. These two dimensions and the nullable rating live in \texttt{trip\_detail}, whose \texttt{trip\_id} is both primary and foreign key. Thus the SQL allows at most one detail row per Trip; the fixed-seed generator supplies exactly one. The generator also keeps ratings on completed trips only. Those cross-table rules are checked in data validation, not enforced by the rating-range \texttt{CHECK} alone.

\subsection{Normalization}
We checked all eight tables using the 1NF--3NF tests taught in Lecture~08. Each column holds one value, so the tables satisfy 1NF. Every declared candidate key is a single column; no non-key attribute can depend on only part of a composite key, so they satisfy 2NF. Names of passengers, drivers, tiers and zones are stored in their own entity tables rather than repeated with every Trip; under the stated business dependencies, no non-key attribute depends transitively on a key within one table, so the present schema satisfies 3NF. The detailed table-by-table check is recorded in \texttt{01\_docs/b5\_normalization\_review.md}.

For a concrete 3NF example, suppose an unnormalised \texttt{TripRaw} also stored \texttt{psg\_name}. The dependencies would be \texttt{trip\_id} $\rightarrow$ \texttt{psg\_id} $\rightarrow$ \texttt{psg\_name}. Since one passenger may take many trips, \texttt{psg\_id} is not a key of \texttt{TripRaw}; the name would be repeated and could be updated inconsistently. Our existing \texttt{Passenger(psg\_id, name)} and \texttt{Trip(trip\_id, psg\_id, ...)} tables remove that transitive dependency while keeping the link through a foreign key. No change to the teacher's five-table DDL is needed.
