\subsection{The Five Base Tables}
Each \texttt{Trip} has one \texttt{Passenger} and one \texttt{Driver}, identified by the required \texttt{psg\_id} and \texttt{driver\_id} foreign keys. A passenger or driver can appear in many trips. Under decision D-05, a Trip is recorded only after a driver accepts a request, so \texttt{start\_time} records acceptance rather than the passenger's request or boarding time.

Each \texttt{Driver} references one \texttt{Vehicle}. The \texttt{UNIQUE} constraint on \texttt{Driver.vehicle\_id} also means that a vehicle can have at most one driver in this database. The handout's sample diagram shows a broader $N{:}1$ Driver--Vehicle relationship; for the implemented model, we follow the supplied DDL in Listing~17. Each \texttt{Payment} belongs to one Trip, while \texttt{Payment.trip\_id UNIQUE} allows a Trip to have either no payment or one payment. The no-payment case is needed for the handout's query about completed but unpaid trips.

\subsection{The Three Extension Tables}
\texttt{trip\_detail} connects a Trip to one \texttt{service\_tier} and one \texttt{pickup\_zone}; either tier or zone can be used by many detail rows. Its \texttt{trip\_id} is both a primary key and a foreign key, so the database permits \emph{at most one} detail row per Trip. The generator supplies one for every Trip, including those cancelled after acceptance. The four service-tier names come from RideAustin; \texttt{fare\_multiplier} is descriptive and is not used to calculate \texttt{Trip.fare}. The 15 pickup zones are a course-defined setting, not a RideAustin field. These extensions leave all five base tables and their columns unchanged.

The pickup zone supports q09, which counts trips that reached driver acceptance, including later cancellations. It cannot count requests that never found a driver. The tier and nullable per-trip \texttt{rating} support q10, which compares completed-trip counts, average \texttt{Trip.fare}, numbers of recorded ratings and average ratings across tiers. This rating is given by a passenger for a particular trip, not a driver's historical average. The \texttt{CHECK} constraint limits recorded ratings to 1--5; the generator and data checks handle the separate rule that only completed trips can have a rating.

\subsection{Normalization}
We reviewed all eight tables using the 1NF--3NF definitions taught in Lecture~08. Each column holds one value (1NF). All declared candidate keys are single columns, so there is no partial dependency on a composite key (2NF). We also checked that a non-key attribute does not depend on another non-key attribute within the same table (3NF); the table-by-table review is in \texttt{01\_docs/b5\_normalization\_review.md}.

For example, adding \texttt{psg\_name} to \texttt{Trip} would give \texttt{trip\_id} $\rightarrow$ \texttt{psg\_id} $\rightarrow$ \texttt{psg\_name}. A passenger's name would then be repeated across trips and could become inconsistent when updated. In our model, \texttt{Passenger} stores the name once and \texttt{Trip} keeps only the \texttt{psg\_id} foreign key. The same principle keeps tier and zone names in their own tables.
